This is the Go API for the cashback wallet app (`../app`). It moves money: payments, campaign cash back, and redemptions. Correctness of balances matters more than anything else here. Read **Money rules** before changing anything that touches an amount, an account or a transaction.

## Stack

- Go (see `go.mod`), Gin for HTTP, routes under `/v1`.
- PostgreSQL 18 via pgx v5 (`pgxpool`).
- SQL is hand-written in `queries/` and compiled to typed Go in `internal/db/` by **sqlc** (pinned in `go.mod` as a tool).
- Schema changes are **goose** migrations in `migrations/`, embedded in the binary and applied on startup.
- Redis 8 (go-redis v9) for idempotency and the cash back budget gate.
- Docker Compose runs `db`, `redis` and `server`; the image is a static binary on distroless.

## Commands

```bash
docker compose up -d --build                      # Postgres, Redis, server on :8080
go tool sqlc generate                             # after editing queries/ or migrations/
go tool sqlc diff                                 # fails if internal/db is out of date
gofmt -l . && go vet ./...
go test ./...                                     # unit + handler tests (no DB needed)

# Integration tests run only when these are set. Use a throwaway database.
docker compose exec db createdb -U cashback cashback_test   # once
TEST_DATABASE_URL='postgres://cashback:cashback@localhost:5432/cashback_test?sslmode=disable' \
TEST_REDIS_URL=redis://localhost:6379/15 go test ./...

# Local data (DATABASE_URL from .env.example)
go run ./cmd/seed                                 # demo users, accounts, history (safe to re-run)
go run ./cmd/campaign create --name "Launch 5%" --currency IDR --rate-bps 500 \
  --min 20000 --daily-cap 50000 --budget 10000000 --round-to 1 --starts-at now
go run ./cmd/campaign list | end <id>
go run ./cmd/campaign gate <id> db|shadow|redis    # switch budget enforcement (needs REDIS_URL)
go run ./cmd/campaign reconcile <id>               # one reconciler pass: drift, leaks
```

Run `gofmt`, `go vet`, `go tool sqlc diff` and the full test suite (with both `TEST_*` URLs) before declaring a change done. Anything touching money needs an integration test, not just a handler test with fakes.

## Layout

| Path | What lives there |
|---|---|
| `main.go` | Config from env (`PORT`, `DATABASE_URL`, `REDIS_URL`, `CASHBACK_WORKER=off` to skip the background worker and reconciler), wiring, `setupRouter` |
| `*.go` (package `main`) | HTTP handlers, one file per area: `auth`, `users` (`requireUser`), `accounts`, `transactions` (also the `store` interface and `pgStore`), `payments`, `cashback`, `redeem`, `idempotent` (shared idempotency helper) |
| `*_test.go` (package `main`) | Handler tests against `fakeStore` / `fakeIdem` in `store_test.go` |
| `internal/database` | Multi-statement money operations that need a DB transaction: `Pay`, `Redeem`, `LaunchCampaign`, `EndCampaign`, `Migrate`; the budget gate's payment side (`gate.go`), award worker (`worker.go`) and reconciler (`reconcile.go`). Integration-tested. |
| `internal/db` | **Generated by sqlc. Never edit by hand.** |
| `internal/money` | `Money{Minor, Currency, Exponent}`, `Decimal()` and `Parse()`: exact conversion between minor units and decimal strings |
| `internal/cashback` | Pure award maths (`Award`): rate, minimum, daily cap, budget |
| `internal/idempotency` | Redis-backed `Store`: lock a key, cache the response, replay |
| `internal/budgetgate` | Redis budget gate: one Lua script per operation (reserve, release, seed, snapshot, …) on per-campaign counters |
| `internal/httpx` | JSON error shape, request logging (`RequestLogger`, `AddToLogger`) and panic recovery |
| `internal/logx` | Structured logging: JSON `slog` with central redaction, per-request logger (`logx.From(ctx)`) |
| `internal/dbtrace` | pgx tracer: per-request database totals for the access log, slow-query logs by sqlc name |
| `migrations/` | goose SQL, embedded via `migrations.go` |
| `queries/` | sqlc input |
| `cmd/seed` | Demo data. Never put demo rows in a migration. |
| `cmd/campaign` | Launch, list and end cash back campaigns (no admin API yet) |

Handlers stay thin: validate input, call the `store`, map the result to JSON. Anything needing several statements in one DB transaction goes in `internal/database` and is exposed through the `store` interface, so handler tests can fake it.

## Money rules

These are deliberate decisions. Don't relax them without discussing it.

1. **Amounts are integers of the minor unit.** Columns are `BIGINT` named `*_minor` (sen for IDR: Rp 35.000 = `3500000`). `currencies.minor_unit` holds each currency's ISO 4217 exponent (IDR 2, USD 2, JPY 0). Never use `float`, `REAL`, `DOUBLE PRECISION`, `NUMERIC` without a reason, or Postgres `MONEY` (it depends on locale).
2. **On the wire, money is a decimal string plus a currency:** `{"value":"-35000.00","currency":"IDR"}`, produced by `money.Money`'s JSON marshalling. Incoming amounts are parsed with `money.Parse` (positive only, no more decimals than the currency allows, rejects overflow). JSON numbers are never used for money, because JavaScript can't represent large ones exactly.
3. **Signs:** `transactions.amount_minor` is negative for money out. A CHECK enforces `kind = 'out'` ⇔ negative, and zero is rejected. Request amounts are always positive; the server applies the sign.
4. **Stored balances.** Each account has `balance_minor`, which must always equal `SUM(amount_minor)` of its transactions. Every write changes the balance and inserts the transaction **in the same DB transaction**. `ReconcileAccounts` checks this, and integration tests assert it after every scenario.
5. **Double-entry for movements between accounts.** Campaign funding, cash back awards and redemptions are always a pair of transactions that sum to zero. `CampaignFlowImbalance` and `ReconcileAwards` check this. (Seeded opening balances and payments to merchants are still single-entry; merchants aren't accounts.)
6. **Overdraft protection is one conditional statement:** `DebitAccount` is `UPDATE … SET balance_minor = balance_minor - $amt WHERE id = $id AND balance_minor >= $amt RETURNING …`. No row means insufficient funds. Never read the balance, compare in Go, then write; that races. A `CHECK (balance_minor >= 0)` backs it up for every account except `funding`.
7. **Lock order, to avoid deadlocks:** the user's main account → the campaign (and its account) → the user's cash back account. `Pay` and `Redeem` both follow it. Keep any new money operation consistent with it.
8. **Timestamps** are `TIMESTAMPTZ`, set by the server (`time.Now()`, or `PayParams.Now` in tests), never by the client. The API sends RFC 3339 in UTC; the app converts to the device's time zone.

## Idempotency

Every money-moving endpoint (`POST /v1/payments`, `POST /v1/cashback/redeem`) requires an `Idempotency-Key` header (8–128 of `[A-Za-z0-9_-]`; the app sends a UUID per attempt and reuses it on retry). Two layers:

1. **Redis** (`internal/idempotency`, used through `runIdempotent` in `idempotent.go`): `SET NX` locks the key per user (`idem:{userID}:{key}`) with a fingerprint of the request body.
   - A finished request replays its cached status and body with `Idempotent-Replayed: true`.
   - A request still running gets 409 `in_progress`.
   - The same key with a different body gets 422 `idempotency_key_reused`.
   - If Redis is unreachable, the endpoint returns **503 and does nothing** (fail closed).
   - Definite outcomes (success and business refusals such as `insufficient_funds`) are cached for 24 hours. Unexpected errors release the key so the client can retry.
2. **Postgres backstop:** the key is stored on the transaction rows, with `UNIQUE (account_id, idempotency_key)`. If Redis lost the key, the second insert conflicts, the attempt rolls back, and the original result is returned (`Replayed`). This is what guarantees "never twice"; Redis only makes it fast and blocks concurrent duplicates.

Fingerprints are prefixed with the operation (`"payment"`, `"redeem"`), so a key can't be replayed across endpoints. A new money-moving endpoint must use `idempotencyKey` + `runIdempotent` and must store the key on its transaction rows.

## Accounts and users

- `users`: email is unique and lower-case.
- `accounts`: `kind` is `main` or `cashback` (owned by a user, one per user, kind and currency), or `campaign` or `funding` (system accounts, `user_id IS NULL`, one funding account per currency).
- `UNIQUE (id, currency)` on accounts plus a composite FK from `transactions` and `campaigns` stops a row in one currency landing on an account in another.
- User-facing queries filter by `user_id` and account `kind`, so system accounts never reach the API.

## Auth (demo only)

There is no real authentication. Sign-in looks up an existing email (`no account for this email` → 401) and returns the user. The app then sends `X-User-ID: <uuid>` and `requireUser` loads the user from it. **Anyone who knows a user id can act as them.** This lives in one middleware on purpose: replace `requireUser` with a token check when real auth arrives; handlers only use `currentUser(c)`.

`requireUser` caches users it has loaded for 30 s (`userCache` in `users.go`, at most 10,000 entries), so most requests skip the `GetUser` query. Unknown ids are never cached and are refused every time. Users aren't deleted while the server runs, so the cache only delays noticing a re-created database; restart the server after re-seeding into a fresh database.

## Cash back campaigns

- **One live campaign per currency**, enforced by an exclusion constraint (`campaigns_no_overlap`). Future campaigns can be scheduled; back-to-back is fine.
- **Rules per campaign:** `rate_bps` (500 = 5%), `min_spend_minor` per payment, `daily_cap_minor` per user per day, `award_increment_minor` (rounding unit; IDR campaigns use whole rupiah), `budget_minor`, `timezone`.
- **The budget is a real account.** `LaunchCampaign` moves the budget from the currency's `funding` account (the only account allowed to go negative) into a new `campaign` account. "Budget remaining" is that account's balance minus awards still pending (`cashback_pending`). `EndCampaign` returns the leftover that isn't owed to pending awards to funding.
- **Each campaign has a budget gate** (`campaigns.budget_gate`), switched with `cmd/campaign gate` (`Reconciler.SetGate`), never by hand:
  - `db` (default): awarding happens inside `Pay` under the campaign lock (below).
  - `shadow`: as `db`, plus each award is mirrored into the Redis counter after commit and any disagreement is logged (`budget gate disagreement`). Nothing acts on Redis. Use it before switching a campaign to `redis`.
  - `redis`: `Pay` reserves the award with one Lua script (`internal/budgetgate`) and writes a `cashback_pending` row in the payment's transaction, **without the campaign lock**. The award worker (`RunAwardWorker`, every server runs one) credits pending awards in batches of up to 100, under the campaign lock but off the payment path. Each campaign's batch is one `RecordAwards` statement: one debit of the total, one credit per cash back account, all ledger and award rows. If the account can't cover the total, the worker credits that batch one award at a time with `RecordAward` and marks only the uncoverable awards failed. The response says `status: "pending"`; `/v1/accounts` shows it as `pending` on the cash back account, and it can't be redeemed until credited.
- **The database is the truth; Redis is only the gate.** What's left = campaign account balance − pending. The Redis counter should equal that minus reservations still in flight. The reconciler (every 5 s, every server; one at a time per campaign via a Redis lock) reads Redis, then the database in one REPEATABLE READ snapshot, then Redis again. That gives the exact drift even under load, because only it removes committed reservations from the in-flight list. It corrects drift with `INCRBY` and logs `budget gate drift`. It also releases reservations older than `GateSettleTime` that never reached the database.
- **Gate failure fails closed.** A Redis error or the 50 ms reserve timeout means no cash back (reason `unavailable`), never a failed payment. Five failures in 10 s on one server degrade the campaign (`gate_degraded_at`). Payments then award nothing for `GateSettleTime` (15 s: `MaxPayDuration`, the longest a reserving payment can still commit, plus margin), then award under the campaign lock with budget = balance − pending. The reconciler recovers the gate once Redis answers: under the campaign lock it reseeds the counter and clears the flag. Payments still 503 if Redis is fully down, at the idempotency layer, before the gate.
- **Switching is safe in both directions.** Towards Redis: seed the counter under the campaign lock, then switch; payments waiting on the lock re-read the gate. Back to `db`: close the counter (`unavailable` meanwhile), wait until every reservation has committed or been released, then switch under the lock. Pending awards keep draining and the lock path subtracts them. A payment that holds a Redis reservation releases it if its transaction rolls back, but **not** if `COMMIT` itself errors, because the commit may have happened. The reconciler decides from the database.
- **Never** write to `cashback_pending` or the Redis keys by hand, add a foreign key from `cashback_pending` to `campaigns` (checking it takes a KEY SHARE lock on the hot campaign row in every payment), or reseed a counter outside `SetGate`/`Recover`.
- **Awarding under the lock (`db`, `shadow`, degraded `redis`)** happens inside `Pay`, in the payment's DB transaction. `GetActiveCampaign` (no lock) picks the path first. Then two statements: `LockActiveCampaign` locks the live campaign and its budget account and returns the budget, the user's awards for the campaign day (credited and pending) and their cash back account; then, after `cashback.Award` computes the amount, `RecordAward` debits the campaign account, credits the user's cash back account, writes both ledger rows and the `cashback_awards` row that links them to the payment, and ends the campaign if the budget hit zero. Under the lock, `Pay` re-checks the gate: a payment that waited through a switch takes the new path.
- **Keep the campaign lock short.** Every awarding payment in a currency queues on that one row, so the time from `LockActiveCampaign` to `COMMIT` caps throughput (about 1,300 awards/s locally, 3 round trips plus the commit). Don't add statements between them; anything that doesn't need the lock goes before it.
- **Lock the rows whose values you read.** Under READ COMMITTED, a `SELECT … FOR UPDATE` that waits re-reads only the locked rows; columns from other joined tables can be from before the wait. That's why `LockActiveCampaign` and `LockCampaign` lock the budget account (`FOR UPDATE OF c, a`) as well as the campaign.
- **Budget edge:** if the award is bigger than what's left, the user gets what's left and the campaign ends at exactly zero (`ends_at` is set in the same transaction). There is no overspend and no stranded remainder.
- **"Per day" is a calendar day in the campaign's time zone** (`Asia/Jakarta`), computed in Postgres from the server timestamp (`(ts AT TIME ZONE tz)::date`), never from the device. Travelling or changing the phone's clock can't game it. `resetAt` (next local midnight, as UTC) is returned so the app can display it.
- **Payment responses** carry `cashback: {amount, reason, status}` or `null` when no campaign is live. `reason` is `awarded`, `below_minimum`, `daily_cap_reached`, `budget_exhausted` or `unavailable` (the gate couldn't check the budget). `status` is `pending` (reserved by the gate, credited shortly) or `credited`. A Redis idempotency replay returns the original body, so it can still say `pending`. A database-backstop replay can only reproduce actual awards (credited or pending); it reports no reason for a payment that earned nothing.
- **Known limits:**
  - In `db` mode every awarding payment locks the one campaign row, so awards in a currency run one at a time (about 0.8 ms each locally, ~1,500 awarding payments/s with 32 payers).
  - `redis` mode took the same load to ~6,000/s. The worker drains about 11,000 awards/s (13,000/s with no payments running), so it keeps up. A sustained rate above that would grow the backlog (logged at error once it's 30 s old).
  - Beyond that, shard the counter (`budgetgate.Gate` is the seam).

## Redemption

`Redeem` moves an amount (the app sends the full balance it displayed) from the user's cash back account to their main account as a double-entry pair. It uses the conditional debit, so it can't redeem more than the balance, and the same idempotency and lock order as payments. It finds and locks both accounts in one query (`LockUserAccounts`, whose `ORDER BY` is the lock order) and builds its result from what it inserted instead of reading it back; keep new money operations to as few round trips as that.

## API conventions

- **Errors** are always JSON `{"error": "message", "code": "machine_code"}`. `code` is optional; the app branches on it (e.g. `insufficient_funds`). Router-level 404/405/panics go through `httpx` too, so they follow the same shape.
- **No internal details in error responses.** For unexpected errors call `httpx.InternalError(c, msg, err)`: it logs the error and returns `something went wrong`. If the client already disconnected (the app gives up after 15 s), the failure is just the cancellation, so it logs at info with `client_canceled` and records status 499 instead of an error and a 500.
- **Lists are newest first and paged by cursor** (`paging.go`): `limit` 1–100 (default 20), `cursor` from the previous page's `nextCursor` (`null` on the last page). A cursor is the last row's `(created_at, id)`; queries compare it as a row value against the `(account_id, created_at DESC, id DESC)` index, with `COALESCE` to "infinity" for the first page so even a generic plan seeks the index. Handlers fetch `limit + 1` rows to know whether there is a next page. Never add an unbounded list.
- **A page must read only its rows.** Filter `transactions` by `account_id` directly (a scalar subquery for one account, `CROSS JOIN LATERAL` per account for several) so Postgres walks the index in order and stops at `LIMIT`. Joining `accounts` to `transactions` and filtering on `a.user_id` looks equivalent but reads and sorts the user's whole history on every page (a join keeps only its outer side's order): 70 ms per page at 200,000 rows, against 0.5 ms. Check a new list query with `EXPLAIN ANALYZE` on a large account.
- **Search text** goes into `ILIKE` only through `likeEscaper`, so `%` and `_` match literally. `?q=` uses its own query, `SearchTransactions`, served by `transactions_name_trgm_idx` (pg_trgm) for rare terms. Its best plan depends on the text (the trigram index for `langka`, walking the date index for `a` or `kopi`), so `pgStore` runs it as an unnamed statement that Postgres plans with the actual text every time; a cached generic plan always picks the trigram index and takes 130 ms for a one-letter search on a long history. There's deliberately no index on `kind`: even the rarest kind (redemptions, ~1%) pages in under 1 ms without one, and every payment would pay to maintain it.
- **Timeouts:** every `/v1` request gets a 10 s context deadline (`httpx.Timeout`, `requestTimeout` in `main.go`), shorter than the app's 15 s. Database and Redis calls take that context, so a query stuck behind a lock stops and frees its pool connection. `httpx.InternalError` turns a deadline into 503 `timeout` (logged at error with `timed_out`); money endpoints release the idempotency key as for any failure. `http.Server` also has read/write/idle timeouts, and SIGTERM drains in-flight requests for up to 15 s (compose's `stop_grace_period` is 20 s).
- **Connections:** the pool has `database.DefaultMaxConns` (20) connections unless `DATABASE_URL` sets `pool_max_conns` (pgx's own default, the CPU count, is too small in a container). `Pay` and `Redeem` may use at most half of them at once (`pgStore.money`); more wait in Go without a connection, until their request deadline. Awarding payments queue on the campaign lock, and without this they'd hold every connection while reads like `/v1/accounts` waited behind them (7 ms p50 instead of 0.3 ms in the load test). Route any new money operation through the same slots.
- **Versioning:** `/v1` may change while the app is unreleased. After release, breaking changes go in `/v2`.

## Logging

- **Format:** JSON lines on stdout via `log/slog`, set up in `main.go` (`LOG_LEVEL`: debug, info, warn, error).
- **Getting a logger:** in a handler, `logx.From(c.Request.Context())`. It carries `request_id` and, after `requireUser`, `user_id`; money endpoints add `idempotency_key`. Errors go in as `logx.Err(err)`. Don't use the `log` package or `fmt.Print` in the server.
- **Request ids:** `RequestLogger` writes one access line per request (method, route template, status, duration, response size, client IP truncated to /24 or /48, and database totals: see below). It accepts the client's `X-Request-ID` when it's well-formed, otherwise generates one, and always returns it, so an error a user reports can be found. The app keeps it on `ApiError.requestId`.
- **Database time** (`internal/dbtrace`, set as the pool's tracer in `database.Open`): each access line has `db_queries`, `db_ms` (running queries, including waits on row locks such as the campaign's) and `db_wait_ms` (waiting for a pool connection or a money-operation slot). `duration_ms` far above both means time in Go, Redis or the network. Queries taking `database.SlowQuery` (100 ms) or more are logged at **warn** as `slow query` with the sqlc name (`"query":"LockActiveCampaign"`), the request id and `failed`; at `LOG_LEVEL=debug` every query is logged that way. Queries are named, never logged as SQL text or arguments. `TestPayRoundTrips` pins an awarding payment in `db` mode at 7 queries.
- **Events logged:** sign-in outcomes, auth rejections (reason only), `payment completed` / `payment declined` (transaction, merchant id, amount, cash back and reason), `campaign ended: budget used up`, `redemption completed` / `declined`, every idempotency decision (Redis replay, in-progress, key reused, database-backstop replay at **warn**, Redis unavailable at **error**), panics with stack traces, and go-redis's own messages (as `library log`, via `logx.Library`). Budget gate events:
  - `budget gate failed` (warn), `budget gate degraded` (error), `budget gate recovered`, `budget gate switched`
  - `budget gate disagreement` (shadow), `budget gate drift` (warn; error at 100 award increments or more), `budget gate released leaked reservations`
  - from the worker: `cash back backlog` and `pending awards failed and need resolving` (error) When adding a money-moving endpoint, log its outcome the same way.
- **Never log:**
  - request or response bodies, or headers
  - balances
  - passwords, tokens, or the `X-User-ID` header (the demo credential)
  - raw emails
  - connection strings with credentials

  `logx` redacts by key (`password`, `authorization`, `token`, `x-user-id`, …), masks `email` values (`a***@e***.com`), and scrubs every string and error for URLs with passwords, `key=value` secrets, bearer tokens and email addresses. That's a safety net, not permission. `logging_test.go` and `internal/logx` tests check it; add a case when you add a new kind of sensitive data.
- **Allowed:** ids (user, transaction, campaign, idempotency key, request), merchant ids, amounts and currencies, reasons and status codes.

## Database changes

- Add a new numbered migration with `-- +goose Up` / `-- +goose Down`; **never edit a migration that has been applied anywhere**. Build indexes on existing tables with `CREATE INDEX CONCURRENTLY` in a `-- +goose NO TRANSACTION` migration (see `00002`), so the build doesn't block payments. `00001_init.sql` is the whole schema as of the first release: the development migrations were squashed into it before anything reached production. A database created before the squash still records versions 1–5 and would silently skip new migrations numbered 2–5, so recreate it: `docker compose exec db dropdb -U cashback cashback`, `docker compose exec db createdb -U cashback cashback`, restart the server, then `go run ./cmd/seed` (same for `cashback_test`).
- Put invariants in the schema (CHECK, FK, UNIQUE, EXCLUDE) as well as in code. Name constraints you match on in Go (e.g. `transactions_account_idempotency_key`, `campaigns_no_overlap`).
- After changing migrations or queries, run `go tool sqlc generate` and commit `internal/db`. Type overrides (uuid → `string`, timestamptz → `time.Time`, nullable → pointers, date → `time.Time`) are in `sqlc.yaml`.
- Demo data goes in `cmd/seed`, not migrations. Reference data that every environment needs (e.g. `currencies`) may be inserted by a migration.

## Testing

- **Handler tests** (`package main`) use `fakeStore` and `fakeIdem` from `store_test.go`; keep the fakes behaving like the real store (per-user data, `pgx.ErrNoRows`, overdraft refusal, key replay).
- **`internal/database` integration tests** run against real Postgres and commit for real. Use the helpers (`payingUser`, `launch`, `payAt`, `assertLedger`): they clean up after themselves and check every ledger invariant. Concurrency tests (`sync.WaitGroup.Go` against a small balance or budget) are expected for new money paths; run them with `-race -count=10`.
- `PayParams.Now` lets tests place payments either side of Jakarta midnight.
- Budget gate tests (`gate_test.go`, `internal/budgetgate`) need `TEST_REDIS_URL` too. Use `newGateEnv` and `launchGated`, call `creditAll` to run the worker, and check `assertNoDrift` (counter = database) as well as `assertLedger`. Give concurrent payments unique idempotency keys: `UnixNano()` alone repeats within a microsecond on macOS, and a repeated key replays instead of paying.
- If a test run panics, its cleanups don't run and a live test campaign can block every later launch (`campaigns_no_overlap`). Recreate `cashback_test`.
